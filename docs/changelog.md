**Phase 1 backend is done and verified end-to-end, the Phase 2 job runner is in, Phase 3's Gemini classify-and-extract call is live, and Phase 4's OCR tier is in and live-verified.** Flyway `V1__init.sql` (full schema), Supabase JWT resource server, `POST/GET /v1/saves`, and a Postgres-backed queue that is now drained by a real runner — `FOR UPDATE SKIP LOCKED`, per-group exclusion so one user cannot occupy a 1–2 slot pool, three error paths, and a stale-claim sweep. The extraction cascade behind it is in too — a `--dump-single-json` probe, then platform captions, VTT-to-prose, and a yt-dlp error table that decides permanent vs retryable. **It now runs against a real yt-dlp** (2026.07.04, with ffmpeg, both on the dev machine's PATH); the opt-in `YtDlpLiveTest` drives it against a live video. **Steps 3 and 4 are in as of 2026-07-31**: ASR (yt-dlp audio download → ffmpeg downmix → Groq Whisper, a different provider so it costs no Gemini RPD) and the non-video branch (Readability4J for plain links, PDFBox for PDFs) — an "unsupported URL" from yt-dlp's probe now falls through to link extraction instead of failing the save, and a `.pdf` URL skips yt-dlp entirely. Unlike the caption path and the Gemini call, **neither has been run against a real network yet** — 46 new tests all mock the HTTP/process layer (`GroqClient` and `LinkExtractor`/`PdfExtractor` bind `MockRestServiceServer`, matching the pattern `GeminiClient` established), so the "mocked process hides real bugs" lesson from both earlier incidents has not yet been tested against this code.

**Phase 4's visual tier — keyframes, local OCR and the escalation gate — landed 2026-08-01 and is live-verified against real ffmpeg 8.0 and real tesseract 5.5.0.** `pipeline/ocr/` holds the whole tier: a bounded worst-quality video download, one ffmpeg pass that cuts deduped keyframes into a colour branch and an OCR-prepped grey branch, tesseract read per frame in TSV mode for its per-word confidence, a vote across frames, and a quality gate that either passes the text to the ordinary cheap classify call or escalates the sharpest frames to one Flash vision request. 57 new tests, and — unlike ASR and the link/PDF branch — an opt-in `OcrLiveTest` that drives the real binaries end to end **with no network** (it renders its fixture videos with ffmpeg), so the toolchain check can run anywhere.

**Running the real binaries overturned two things the plan itself specified — see [docs/testing.md](docs/testing.md#what-running-the-real-binary-found-the-second-time-visual-tier-2026-08-01).** Both are worth carrying into any future frame or OCR work:

- **`select='gt(scene,0.25)',mpdecimate` selects *zero* frames from a static card.** Frame 0 has no predecessor to differ from and nothing afterwards changes, so scene detection never fires — on precisely the overlay-only Reel this tier exists for. The selector must also take frame 0 (`+eq(n,0)`) and a periodic sample (`+not(mod(n,150))`), with `mpdecimate` left in to collapse the duplicates that adds. Measured: 0 frames before, 1 after.
- **Histogram equalisation makes overlay OCR dramatically worse.** The documented "upscale, grayscale, CLAHE contrast" advice assumes a photographic background with a gradient to flatten; overlay text is high-contrast and bimodal *by design*, and a global remap hollows the glyphs. Same frame, real tesseract: plain upscale+grey read **16 of 16 words at mean confidence 95**; adding `histeq` read **7 garbled tokens at 22** and lost a line. 22 is below the escalation floor, so the "recommended" preprocessing would also have spent a Flash vision request fixing damage it caused.

Also confirmed on real content: tesseract's failure shape is **confident** symbol soup (`|` at 72, `=` at 91 on a talking-head clip), so a gate watching per-word confidence alone waves it through. The alphabetic-token-ratio signal is what catches it.

**Running the real yt-dlp broke three assumptions earlier — same doc, [first section](docs/testing.md#what-running-the-real-binary-found).** Two are worth carrying into any future yt-dlp work: **`--sub-langs` entries are regexes, and yt-dlp synthesises translated tracks named `<source>-<target>`**, so `en.*` matched 29 languages and earned an HTTP 429 partway through one fetch — always use exact codes. And **auto-generated VTT is several times the size of an uploaded track while carrying less text** (43,947 bytes → 4,284 chars of prose, against 8,456 → 4,443), so ranking caption files by size systematically picks the worse source; rank on parsed prose instead. Also: yt-dlp exits non-zero if *any* requested track fails, so read the output directory before trusting the exit code — a rule the frame extractor now follows too.

**The Render deployment surfaced a failure mode no local run ever hit: YouTube's "Sign in to confirm you're not a bot" on Render's datacenter IP, for every YouTube probe.** This is a different failure from anything `YtDlpLiveTest` exercises, because that test runs from a residential dev machine's IP — cloud IPs get the challenge, home IPs mostly don't. Two mitigations were tried against the live deploy between 2026-08-02 and 2026-08-05, and the outcome is now known for both, not guessed:

- **Cookies alone did not clear it, confirmed.** `WEAVR_YTDLP_COOKIES_BASE64` decodes to a `--cookies` file at startup (`YtDlpClient.initCookies`) — present and correct in the probe command, and the job still failed. A cookie exported on a residential machine and replayed from an unrelated cloud IP is itself a bot signal, and the `web` player client's challenge additionally wants a PO token that cookies don't supply.
- **`--extractor-args youtube:player_client=tv,android,web` (`WEAVR_YTDLP_PLAYER_CLIENTS`) also failed, confirmed, not just untested.** 8 fresh real YouTube URLs (4 Shorts, 4 regular, none reused) posted to the live deploy with both cookies and the player-client override in place, command line confirmed correct in logs — all 8 hit the identical bot-check error. This ruled out a config bug and pointed at Render's Oregon IP itself being blocked by YouTube independent of auth method, which is why the fix that followed changes the mechanism rather than the arguments.
- **A live-cookies file was accidentally committed while debugging this** (`www.youtube.com_cookies.txt`, real session cookies) and had to be scrubbed from tracking; `*cookies.txt` is now in `.gitignore`. The lesson is generic: any debug step that writes a credential to disk for inspection is one `git add .` away from leaking it, and the gitignore entry should land in the same commit as the debug logging, not after.

**`RapidYtClient` (landed 2026-08-05) sidesteps the bot check instead of negotiating with it, and this one is confirmed live, not just deployed.** A two-call RapidAPI path (`ytstream-download-youtube-videos`) fetches metadata and a caption-track XML without yt-dlp ever contacting YouTube directly, tried first in `ExtractionCascade` for any URL `RapidYtClient.extractVideoId` recognises, falling through to the unchanged yt-dlp path on empty result or failure. Gated by `WEAVR_RAPID_YT_API_KEY` — blank disables it, same opt-in shape as Groq and the enrichment keys. **Render's own logs show two real YouTube URLs (a Shorts link and a `youtu.be` link) each clearing `RapidAPI probe succeeded` and completing the full pipeline — `process_save` → `classify_save` → `enrich_save` → `embed_save`, all four jobs `succeeded`** — at 22:42 and 22:43 UTC on 2026-08-04, on the first deploy that actually contained the feature (the commit that added `RapidYtClient` failed to build three times first — Maven runs the test suite as part of the Docker build, and the constructor signature change broke `ExtractionCascadeTest` until a follow-up commit fixed it; a red build blocks the *deploy*, not just CI, on this setup).

**Instagram, unlike YouTube, is not walled off on Render — confirmed by 7 real Reels, not assumed.** One solo test, then 6 back-to-back roughly 5-6s apart to check for rate-limiting under a burst: all 7 cleared yt-dlp's ordinary probe directly (the same command that fails every time for YouTube), no retry, no slowdown, no bot-check error, extracting 117–19,254 chars depending on how much caption text each post carried. This overturns the standing planning assumption ("Instagram increasingly requires authentication, cookies risk a ban") as a *default* — it may still be true for specific accounts or at higher volume, neither of which is tested, but it is not a wall on the first 7 tries from this IP the way YouTube's bot check is on the first 1.

**The same test window surfaced a real, separate problem: the DB pool is too small for concurrent load.** One request during that session hit `weavr-pool - Connection is not available, request timed out after 12502ms (total=3, active=3, idle=0, waiting=1)` and surfaced as an unhandled exception — `WEAVR_DB_POOL_MAX=3` (`render.yaml`, sized for Supabase free tier's scarce connections) was fully saturated by the concurrent test traffic, and the fourth request waited 12.5s before giving up rather than queuing successfully. **Fixed 2026-08-05**: bumped to 5 in `render.yaml`, still inside the ~5–10 range this doc's own Supabase guidance calls for — 3 undershot it. Not re-measured against real concurrent-save load, just against the manual burst that found it.

**A second, unrelated bug surfaced from the same 7-Reel Instagram batch: the Gemini fallback model was silently 404ing on every call, on this project's own key.** `application.yml`'s `fallback-model: gemini-2.5-flash` — the model that both the confidence-retry quality backstop and the OCR vision-escalation tier share as their one fallback — returns `"This model models/gemini-2.5-flash is no longer available to new users"` from the real API. Confirmed by reproducing the exact `generateContent` call directly against the production key: 404, verbatim message above. The trap is that `ListModels` still lists `gemini-2.5-flash` as supporting `generateContent` — the model catalog and per-project access are two different things, so nothing about inspecting available models would have caught this; only calling it does. Both fallback consumers were failing **closed** with no save-level error (silently keeping the primary's low-confidence result, or skipping vision escalation), so there was no user-visible symptom pointing at it — this had likely been broken since whenever the primary model was bumped to the 3.x line, unnoticed. **Fixed 2026-08-05**: `gemini-3.6-flash`, verified against the real key before landing (confirmed via a live `generateContent` call, not assumed from the model list). Unit tests for both consumers build their own `GeminiProperties` fixtures by hand and never read `application.yml`, so none of them could have caught this either, and none needed changing for the fix.

**The weekly digest landed 2026-08-06 — the last remaining sample content in the app, and the first feature deliberately built with no scheduler at all.** `GET /v1/digest` (`digest/`, `V8__digests.sql`) checks for a cached row at `(user_id, week_start)`; if none exists it enqueues `generate_digest` and returns `202 pending`, and every later request that week reads the cached row. No cron generates these ahead of time — generation only happens when someone is actually looking at Home, which is what "budget digests explicitly, don't let them eat the day's save capacity" (this doc, above) turns into in code: nobody pays for a digest nobody opens. Three decisions carried forward from earlier features rather than reinvented:

- **`week_start` is `UsageService.weekStart()`**, made public for this — the same Monday-UTC boundary the Act's weekly cap already uses. One definition of "this week," not a second one that could quietly drift from the first.
- **The write on conflict is a full overwrite, not an increment** — `ShoppingListService`'s accumulation bug (garlic 7→10 on a re-delivered job) is exactly the failure shape a running total invites, and a digest recomputed from the same week's saves is idempotent by construction as long as the write replaces.
- **Title lookup reuses `SpaceService`'s `coalesce(structured_data->>'title', structured_data->>'name')`** rather than a third independent guess at which field a knowledge type uses — the same trap that broke `saveTitle()` app-side and `search_tsv` before that.

`GeminiClient.summarizeDigest` is plain-text in, plain-text out, structurally identical to `transcribeFrames` and for the same reason: the output is prose for a UI label, and a `responseSchema` would only wrap it in an escaping layer. It draws from the same primary budget pool as saves and Acts (`budget.acquire()`, not a separate allowance) and logs to `gemini_calls` with a `null save_id` — a digest isn't about any one save, which is exactly what that column being nullable was for. Verified: full backend suite green, the new `GeminiClientTest` cases pin the request shape (no images, no schema) and the UTF-8 decoding path; app side typechecks and bundles. **Deployed and confirmed live the same day**: Render's own logs show `Migrating schema "public" to version "8 - digests"` followed by `Successfully applied 1 migration`, and the job runner's startup line lists `generate_digest` among its registered types. Not yet exercised against a real week of saves through the actual endpoint, only confirmed to have deployed cleanly.

**The GitHub Actions deploy-hook workflow broke on 2026-08-05, and the first fix was wrong before the second one was right — worth carrying forward as a general lesson about verifying an assumption rather than patching around it.** `deploy.yml` piped the Render deploy hook's response straight into `jq .`; a push crashed it with `jq: parse error: Invalid numeric literal at line 2, column 0`. **First pass, wrong:** assumed the hook always returns JSON like Render's authenticated Deploys API does, and just made the failure easier to read (capture status and body separately, fail loudly if the body isn't JSON) — still built on the same unverified assumption the original script had. **Second pass, right, after actually looking at what came back:** the real response to a successful trigger is `HTTP 202` with a plain-text `Accepted` body — not JSON at all. The fix that matters is not "handle the JSON parse failure better," it's "stop requiring JSON in the first place" — status code is now the only success signal, and the body prints for visibility (pretty if it happens to parse, raw otherwise) without gating anything. Neither failure ever touched the actual deploy: Render's own native auto-deploy-on-push is a separate, independently-working trigger, which is exactly why this sat broken without anyone noticing until a screenshot surfaced it.

**Everything downstream is a `JobHandler`, not a change to the runner.** The cascade, the Gemini call, enrichment and embedding each register a handler keyed by `jobs.type`. Outcomes are signalled by exception: `RetryAfterException` reschedules *without* spending an attempt (this is what stops a quota rejection from burning the retry budget), `PermanentJobException` fails immediately with a user-safe message, anything else costs an attempt and backs off exponentially.

**The Gemini call has run against the real API and produced real structured saves — twice, watched live, on 2026-07-30.** That run also surfaced a decoding bug: Gemini's response carries no charset on its `Content-Type` header, and reading it with `.body(String.class)` let Spring guess a charset instead of following the JSON spec's UTF-8 default — accented text arrived as mojibake (`café` → `cafÃ©`). Fixed in `GeminiClient.classify` by reading `.body(byte[].class)` and letting Jackson's byte-based `readTree` decode it directly. That fix, the primary→fallback model routing and budget guard, and the response-schema registry now have unit test coverage that did not exist before this fix landed — `KnowledgeTypeRegistryTest`, `GeminiBudgetServiceTest`, `GeminiClientTest`, `ClassifySaveHandlerTest` (25 tests). `GeminiClientTest` binds `MockRestServiceServer` to an injected `RestClient.Builder` rather than mocking the HTTP layer away, so its regression test genuinely reproduces the mojibake when pointed at the old `.body(String.class)` code and passes against the fix — verified both ways, not just written to pass.

The full create path has run against live Supabase: sign in (ES256 JWT) → `POST /v1/saves` 202 → `GET /v1/saves/{id}` 200 → list 200. That covers the `@CurrentUser` resolver, the lazy profile upsert, the JSONB mapping, and a commit through the transaction pooler. **Supabase signs with ES256, and `NimbusJwtDecoder` accepts RS256 only by default** — the explicit `.jwsAlgorithm()` call in `SecurityConfig` is load-bearing, and the failure mode is a misleading "no matching key(s) found". Per-area status is in [README.md](README.md#whats-real-vs-stubbed).

**`POST /v1/saves` is now idempotent on a repeated `Idempotency-Key` header** (`V2__save_idempotency.sql`: a partial unique index on `saves (user_id, idempotency_key)`). A retried request — including two concurrent retries racing each other — returns the existing save instead of minting a second one; `SaveServiceTest` covers the happy path and the race. This is a different layer from the job queue's own dedupe: `JobQueue.enqueue` only stops a duplicate *job* for a save id that already exists, so it never protected against the duplicate save id being created in the first place. No caller sends the header yet — the Paste Link tile doesn't need it, and the iOS share extension that will (its background `URLSession` retries a POST on the OS's schedule, not the caller's) is still unbuilt.

**The one Act — recipe → shopping list — landed 2026-08-01 and is verified live** (`V5__shopping_list.sql`, `act/`). One open list per user; one Gemini call normalises ingredient lines into products, quantities and supermarket aisles; the result merges into what is already there. Two real recipes produced garlic at 7 cloves (3 + 4) and olive oil at 4 tbsp (2 + 2). Three things worth carrying forward:

- **A merged line must store each contributor's quantity, not a running total.** The obvious accumulate-on-add implementation is correct exactly once, and the runner re-delivers a job on any transient failure or stale claim — the second delivery took garlic from 7 cloves to 10 with no error anywhere. Storing per-save contributions and recomputing makes the result depend only on *which* recipes are on the list. `ShoppingListService.fold` is static and database-free precisely so that property is testable.
- **The aisle vocabulary must be a closed set in the response schema.** Free-form categories give "Produce", "produce" and "Fruit & Veg" across four recipes, and the grouping that is the entire point falls apart.
- **`usage_counters.acts_used` is written but not enforced.** A one-per-week cap only makes sense once there is a paid tier to escape to, and `subscriptions` is filled by a webhook that does not exist. Counting from the start means the cap can later be set against real numbers. *(Superseded 2026-08-01: the webhook exists and the caps are enforced, behind `weavr.billing.enforce-free-caps`, still off by default for the same reason.)*

**Phase 5's monetisation half, enrichment, and Phase 6's Spaces landed 2026-08-01, all driven live against Supabase** — `billing/`, `enrich/`, `space/`, `V6__billing.sql`, `V7__spaces.sql`. Four things worth carrying into any future work here:

- **Postgres aborts the whole transaction on a failed statement, so a `try/catch` around a write is decorative when it runs inside the caller's transaction.** Recording a `save_added` activity row inside `SaveService.create` hit a foreign key — Hibernate defers the `saves` INSERT past that point — and the catch written to make metering non-fatal caught an exception whose damage was already done; every save into a Space 500'd. Anything that "must never break the thing it describes" needs `REQUIRES_NEW`, and anything referencing a row by FK needs an after-commit hook. **No mocked test can reproduce this**, which is the strongest argument yet for Testcontainers.
- **Derive entitlement from expiry, never from the event type.** `CANCELLATION` means auto-renew off, not access ended — a type-switch cuts off someone who has paid through the period. And webhook delivery is at-least-once *and* unordered, so both guards belong in SQL: `on conflict (id) do nothing` for the first, a `last_event_at <=` clause for the second. Without the ordering guard a delayed retry hands a lapsed user a permanent subscription.
- **Enrichment must run between classify and embed.** The vector is built from `structured_data`, so embedding first permanently omits the director and the address — and re-embedding is not available, because the embed job is deduped on the save id and a second one silently never runs.
- **Every external search API is a nearest-match with no "no result"** — TMDB answers a garbled title, Places answers "Noma" with a coffee roaster. Exactly the k-NN failure the search half hit with `zzzzqqq`, in different clothing, and it needs the same fix: a similarity threshold. Enrichment is additive-only on top of that, so the worst a wrong match can do is add a field rather than overwrite what the user's content said.

**Home → Settings is a container transform rather than a push** (`app/src/motion/`, added 2026-08-01, typechecked and bundled only — the transition itself has still never been watched). The Settings surface grows out of the gear tile on Home and collapses back into it on the same spring. Three decisions in it generalise to any future shared-element navigation here:

- **The stack must do no transition of its own** — the route is a `transparentModal` with `animation: 'none'` and `gestureEnabled: false`. A stack animation cannot be played backwards on demand, so a push/pop pair always cuts at the moment of navigation however well its two halves are matched; owning both directions is the only way a collapse can mirror an expansion. `gestureEnabled: false` matters for the same reason — a swipe-back pops the route and skips the collapse entirely.
- **Measure the source at press time, and navigate from the measurement callback.** `measureInWindow` is asynchronous and the presented screen reads the rectangle in its first animated style, so navigating first expands from a stale rectangle on the very first open. The Home header is inside a `ScrollView`, so a value cached at layout is wrong as soon as the user scrolls, and the anchor needs `collapsable={false}` or Android flattens it out of the native hierarchy and it has no position to measure at all.
- **One module-scope shared value drives both screens.** The surface's geometry, the backdrop blur, the content fade and the shell receding *behind* the modal are one `morphProgress` sampled in different places, so they cannot drift apart. It is not a context because its two consumers sit on opposite sides of a navigation boundary — the route below stays mounted but is not a parent — and because a context delivers by re-render, where the morph has to run entirely on the UI thread. Only the surface animates layout props; the screen inside is a fixed-size subtree moved by `transform`, so the cost does not grow with the screen's complexity.

**Android's half of silent capture is built, as a config plugin, not a hand-edited `android/`.** `app/plugins/withAndroidShareReceiver.js` adds a no-display `ShareReceiverActivity` (`ACTION_SEND` / `text/plain`) and a `ShareUploadWorker` — a `CoroutineWorker` that POSTs to `/v1/saves` under a network `Constraints`, exponential backoff, and a per-share idempotency key generated once at enqueue and carried through every retry. Both run in-process, so unlike iOS there is no separate-process boundary to bridge across: `app/src/share/nativeShareConfig.ts` mirrors the session and the `openAppWhenSaving` toggle into a plain JSON file in the app's private files dir (`expo-file-system`'s `Paths.document`, which *is* `context.filesDir` on Android), and the native side reads it directly. Verified by regenerating the native project (`expo prebuild -p android --clean`) and inspecting the output — manifest entry, Gradle dependency and Kotlin sources all land correctly and idempotently on a second run — and by typechecking; **not run on a device or emulator**, since this machine has no Android SDK. One known gap: the mirrored access token can go stale while the app is backgrounded (the refresh timer is deliberately stopped then, same as the API client), and nothing yet re-mints it inside the worker — see the root README's Known gaps. *(Superseded 2026-08-12 below: the original version's "toast first, durability maybe" ordering was itself a reliability bug, now fixed.)*

**The Android capture path had a real reliability bug, reported as device-dependent, and the fix is a durable local queue landed 2026-08-12.** The symptom: the OS Share Sheet showed "Weavr saved," but the item was sometimes missing when the app was reopened, reproducing on one device and not another — the signature of a background-kill race rather than a logic bug. The root cause was exactly what the original paragraph above undersells: `ShareReceiverActivity` called `Toast` immediately after `WorkManager.getInstance(applicationContext).enqueue(request)`, but `enqueue()` returns before its write actually lands — it schedules an insert into WorkManager's *own* Room database on a background executor thread. Android is free to kill the process the instant `finish()` returns, which on aggressive OEM battery managers (the plausible explanation for "works on another device") can happen before that background write completes — so the toast had already promised something no durable state backed. Four things generalize:

- **A capture now durably exists before the user is told so, via a store this feature owns rather than one it borrows.** `CaptureStore` (`plugins/android-templates/share/CaptureStore.kt`) is a plain `SQLiteOpenHelper` table — one row per share, `RECEIVED → PERSISTED → QUEUED → PROCESSING → RETRY_PENDING → COMPLETED/FAILED`, with `retry_count` and `error_message` columns. `ShareReceiverActivity.insert()` is a synchronous, blocking SQLite write on the calling thread; the "Saved to Weavr" toast fires only after it returns `true`. RECEIVED is deliberately never a stored row — by definition nothing durable exists yet at that point, so it is log-only, matching the requirement that a queued item must never depend on a state nothing wrote down.
- **Image shares are copied to private storage synchronously too, not just referenced by URI.** The old code held only a `content://` URI granted for this process's lifetime; a delayed WorkManager retry (or a cold-start recovery run, possibly hours later) has no guarantee the source app's provider is still reachable. `copyImageSynchronously` blocks the main thread on a bounded `withTimeoutOrNull(5000)` IO copy before persisting — bounded so a slow or network-backed provider degrades to "Couldn't save this yet. Tap to retry." instead of hanging the activity.
- **Cold-start recovery closes the gap WorkManager's own persistence cannot.** `ShareRecovery.recoverPendingCaptures`, wired into `MainApplication.onCreate` by a new `withMainApplication` mod in the same config plugin, re-enqueues (via `ShareWork.enqueue`, shared with the Activity so both use the identical `enqueueUniqueWork(..., ExistingWorkPolicy.KEEP, ...)` call) everything `CaptureStore` still lists as incomplete. This covers two failure modes a "WorkManager already persists across restarts" assumption misses: the enqueue-write race above, and Force-Stop, which — per Android's documented behavior — cancels *all* of an app's scheduled WorkManager work outright with nothing left in WorkManager's own state to recover from. `CaptureStore` is the source of truth in both cases; FAILED rows (retry budget exhausted) are excluded from recovery on purpose, or a bounded retry policy would become unbounded across enough app restarts.
- **Retry count moved from WorkManager's `runAttemptCount` into the store, because recovery creates a fresh `OneTimeWorkRequest`.** The old workers checked `runAttemptCount >= MAX_ATTEMPTS`, which resets to 0 on every new request object — meaningless once a capture can be re-enqueued by recovery rather than only resumed by WorkManager itself. Both workers now check `record.retryCount` (persisted, incremented via `CaptureStore.incrementRetryAndMarkPending`) and read their payload — URL or the locally-copied image path — from the store by capture id instead of from WorkManager's input data, so a recovery-created request still has both the content and the retry history to work from.

Every stage logs through one `ShareLogger` tag (`WeavrShare`) with the literal bracketed labels this was scoped against — `[SHARE] Intent received`, `[SHARE] URL extracted`, `[SHARE] Persisting capture`, `[SHARE] Capture persisted: <id>`, `[SHARE] Queueing processing`, `[SHARE] Success returned to Share Sheet`, `[PROCESS] Started/Completed/Failed/Retry scheduled: <id>`, `[RECOVERY] Resuming pending capture: <id>` — so `adb logcat -s WeavrShare` on the affected device can show which stage actually fails, rather than guessing between intent handling, local persistence, background processing and sync the way the bug report had to.

**Verified the same way as the original version, with the same gap stated rather than hidden:** `expo prebuild -p android --clean` regenerates all eight `share/` sources plus the `MainApplication.kt` merge cleanly, and a second prebuild on top confirms the `withMainApplication` merge is idempotent (single `@generated begin/end` block, not duplicated) — the same technique already used to verify the manifest entry and the Gradle dependency. `npm run typecheck` is clean (no TypeScript changed; `nativeShareConfig.ts` needed no edit, since the native side still reads the same mirrored JSON file). **Not compiled and not run on a device** — this machine has no Android SDK (`local.properties` absent, `ANDROID_HOME` unset), so the Kotlin was hand-reviewed line by line against the Android/Kotlin/WorkManager APIs it calls rather than built; that is a strictly weaker bar than the rest of this codebase's native-code claims usually clear, and is flagged here for the same reason every other unverified claim in this doc is.

**A pom.xml gap meant the API could not boot at all, and no unit test had caught it.** `GeminiClient`, `GroqClient`, `LinkExtractor` and `PdfExtractor` all inject `RestClient.Builder` assuming Spring Boot auto-configures a prototype-scoped bean for it — true through Boot 3.x, but Boot 4 split that autoconfiguration out of `-webmvc` into `spring-boot-starter-restclient`, never added here. Every test binds a `RestClient.Builder` by hand, so none of them boot a real `ApplicationContext`. Found and fixed by actually running `spring-boot:run` and hitting `POST /v1/saves` with `curl` end to end — real sign-in, a real `202` with a `Location` header, a repeated `Idempotency-Key` returning the same save (the exact contract the Android worker above relies on), and a no-auth request returning the expected empty-body `401`. See the root README's "Also on 2026-07-31" for the full trace.

**The app ran on a real Android device for the first time on 2026-08-01, and the first thing it showed was a bug that typechecking, bundling and a browser dev server had all missed: the bottom nav did not paint at all.** Home rendered correctly — greeting, search bar, digest, and a feed of real saves fetched from the live API, so sign-in and `GET /v1/saves` are now proven on a device rather than only in theory — but neither the floating Home/Library/Spaces pill nor the capture FAB appeared, leaving the app with no navigation. Two things are worth carrying forward:

- **The cause is `TabPane`'s `zIndex: 1` against a `BottomNav` that had no z-index at all.** Painting order puts *any* positive z-index above an element that has none, whatever the source order — so being the later sibling bought the nav nothing, and an opaque full-bleed pane was painted straight over it. The panes' container is a plain view, which does **not** create a stacking context, so the `zIndex: 1` was never contained the way its own comment implies. The fix is an explicit `zIndex: 2` on a full-screen `box-none` nav layer hoisted out of the shell; the hoist alone is not what fixes it, the number is.
- **Do not lean on a transform to contain a z-index.** The hoisted nav renders correctly even without the explicit number, because the shell's `transform` establishes a stacking context that traps the pane's `zIndex` inside it — but that is a CSS behaviour with no guaranteed React Native equivalent, so it would have been a fix that worked in a browser and possibly not on the device it was written for. Measured both ways: with the transform removed and the pane's z-index loose in the root, `zIndex: 2` still holds the nav on top.
- **The pill and the FAB are siblings inside one absolutely positioned root, and only one of them uses `BlurView`.** Both being absent is what ruled out `expo-blur` early. That was a sound deduction which then pointed at the wrong culprit — the newest, least-seen thing in the tree (the `overflow: 'hidden'` shell wrapper) rather than the oldest. **Reproducing it took ten minutes and overturned the answer.**

**How it was reproduced, since there is no emulator here:** `npx expo start --web` on a spare port, a throwaway route mounting the same shell structure with a fake pane (the real one is behind an auth redirect), and headless Chrome (`--headless=new --screenshot --window-size=412,915`) driven straight from the shell. That is now the cheapest app-side visual check available and it should be the *first* move on any rendering bug, not the last — see [docs/testing.md](docs/testing.md). **The nav fix is confirmed on the device**, not just in Chrome: the Capture sheet cannot be reached without tapping the FAB, and it was.

**The Capture sheet then showed the harness's limit, and cost two wrong guesses before the real cause.** The FAB opened a sheet whose tiles painted over the footer text with their rows collapsed to no height. Chrome rendered the same screen *correctly*, which was read first as "an entrance that never finished" and led to a fix that changed nothing. The actual cause:

- **`flex: 1` on a child whose parent column has auto height collapses to zero height in Yoga, and does not in CSS.** `flex: 1` implies `flexBasis: 0`; Yoga resolves a zero-basis child in a container with an indefinite main axis to 0, while CSS sizes an auto-height flex container to max-content and gives the child its content height. `OptionTile`'s `Touchable` carried `flex: 1` for no reason — the width already comes from the wrapping view's `flex: 1` along the *row* axis, and a column parent stretches children horizontally anyway. Every other `flex: 1` in the app is on a row axis, which is why this was the only screen affected.
- **A browser cannot see this class of bug at all, and worse, it reports it as fine.** That is the harness's boundary: it catches paint and z-order, and it is actively misleading on Yoga-vs-CSS sizing. "Correct on web, wrong on device" should now be read as a Yoga sizing rule before anything else is considered.
- **The overflow is what disguised it.** React Native does not clip overflow by default, so the icons kept painting at full size inside a zero-height box — which looks like a stuck animation rather than a collapsed layout. The tiles' faintness was never a symptom either: eleven of the twelve are unimplemented and render at `alpha.disabled` by design.

**`--force-prefers-reduced-motion` is still the right first move on any animated screen**, just not sufficient here. Headless Chrome's virtual clock does not settle Reanimated *springs*, so a plain screenshot catches every sheet mid-flight and proves nothing; that flag makes `useReducedMotion()` return true and renders the settled layout immediately.

**The app runs entirely without a backend as of 2026-08-01, and that is now the default.** `app/src/data/` holds a `Repository` interface with two implementations — `apiRepository` (pure delegation to `@/api/client`) and `mockRepository` (in-memory, no network) — and `USE_MOCK_DATA` in `data/config.ts` picks one. No screen imports `@/api/client` any more; they all take `repo` from `@/data`, so switching environments is that one boolean and nothing else. Four things about it are deliberate:

- **Mock mode covers auth too.** `SessionProvider` hands back a synthetic session and skips Supabase entirely, and `_layout` skips the `MISSING_CONFIG` gate. Otherwise "runs with no backend" is false at the very first screen, and every UI review starts by signing into an account that has to exist somewhere real.
- **The mock repository is stateful, not a fixture dump.** Creating a save prepends it as `processing` and flips it to `ready` on a timer; ticking a shopping item stays ticked. A stateless mock passes every optimistic-update bug in the UI.
- **Latency is simulated (200–400 ms), not zero.** An instantly-resolving repository skips every loading state in the app, which are the states most easily got wrong.
- **The fixtures are shaped like real pipeline output** — `place` names its title `name`, `movie` uses `synopsis`, `recipe` carries `ingredients` — so the real `buildCardModel` renders them through its real branches. Fixtures shaped to whatever the UI wanted would validate nothing.

**AI groups are a recursive tree, not a flat list of categories.** `KnowledgeGroup` holds `subgroups: KnowledgeGroup[]` of its own type, so nesting is unbounded by construction rather than capped at two levels by a separate `Subgroup` shape. That decision pays for itself in the UI: `/group/[id]` renders a group *and* pushes itself for a child, so the navigation stack is the breadcrumb trail, back always goes up exactly one level, and arbitrary depth costs no extra screen. Two smaller rules hold here — a parent's `itemCount` is **derived** from its subtree rather than declared (a hand-written total goes stale the first time a child changes, and a parent claiming 38 while its children sum to 41 is what makes an interface feel untrustworthy), and the card previews **subgroup names** rather than adjectives, because "Movies • TV Series • Anime • +2" tells you how the thing is organised where "Films • Series • Weekend" told you nothing you could navigate by. No emoji or placeholder glyph: `illustration` and `coverImage` sit on the model waiting for the visual design system, and a stand-in icon now would be a thing to remove rather than a thing to replace.

**The tree is served by `GET /v1/groups`, derived per request rather than stored** (`api/.../group/`, verified live 2026-08-02). It is a *view* over `saves`: top level by `knowledge_type`, subdivided by the facet that type already carries — `cuisine`, `genre`, `tags`. Three properties follow, and all three were the reason not to add a table:

- **It costs no Gemini request.** The grouping signal was already produced by the one classify call each save gets, which makes this AI-derived organisation at zero cost against the 500 RPD ceiling — the only kind affordable per user.
- **It cannot go stale.** A stored tree needs invalidating on every classify, re-classify, enrich and delete, and the failure mode of missing one is a folder that lies about its contents.
- **Facet fields are chosen for being closed-ish vocabularies the model repeats.** Cuisines and genres recur across saves, so they cluster; `title` would produce one subgroup per save, which is not a grouping at all.

**`itemCount` counts distinct saves, not memberships — and only running it against a real database showed why.** `genre` is a list, so one film filed under Thriller *and* Drama made the obvious sum report "Watchlist · 2 items" over a library holding a single movie. Every unit test until then used single-valued facets and confirmed the wrong answer. A folder is asked how many things are in it, not how many places we filed them.

**`USE_MOCK_DATA` must never be committed as `true`, and a hook enforces it.** `.githooks/pre-commit` (wired up by the tracked `core.hooksPath`) rewrites the *staged* copy to `false` and leaves the working tree alone — so committing never interrupts local development, and `git status` showing `config.ts` as modified straight afterwards is the mechanism working rather than a mistake. The reason it is a hook and not a habit: mock mode committed is a **silent** outage. A build from `main` would ship an app talking to nothing and looking entirely healthy while it did, because the fixtures are realistic by design. No error, no blank screen, just a disconnected app — much worse than a crash, which at least reports itself.

This reverses, for development only, the earlier call to delete invented content. That decision was about *fiction sitting beside real data with no way to tell them apart*; this is a labelled switch where the whole app is on one side or the other. `apiRepository` now delegates the group methods to a real endpoint (below), and every other section already hides itself when the server has nothing — so the real backend shows no fiction.

**Otherwise it typechecks and bundles, and that is close to all that has been proven.** Treat app-side claims beyond Home's feed and the nav fix as unverified until a device says otherwise. Details and the contrast-picking rationale are in [app/README.md](app/README.md).

**Phase 5's search half landed 2026-08-01 and is verified end to end against live Supabase** — `embed/` and `search/`. A save reaches `ready`, then a separate `embed_save` job embeds a `label: value` profile built from `structured_data` (CA#8 — never the raw caption, which is dominated by filler), and `GET /v1/saves/search` fuses Postgres FTS with pgvector by Reciprocal Rank Fusion (k=60). Proven live: *"somewhere nice to eat in Denmark"* returns a save whose text says **Copenhagen** and never Denmark. Four things worth carrying forward, all of which only the live run showed:

- **`to_tsvector(text)` is STABLE, not IMMUTABLE**, so a generated column must use the two-argument `to_tsvector('english', …)`. And `jsonb_path_query_array(data,'$.*')::text` indexes values only, where `data::text` also indexes the JSON **keys** — "name" and "ingredients" would match every save. Both confirmed by asking the database, because either wrong fails a migration and leaves Flyway needing repair.
- **V1's `search_tsv` could not find a restaurant by its name.** It read `structured_data->>'title'`, but `place`'s field is `name` — the same trap that broke `saveTitle()` app-side — and `movie` uses `synopsis`, not `summary`. Arrays were invisible entirely. V3 replaces it with a weighted vector (A=title/name, B=prose, C=everything else); V4 strips the `[unclear]` sentinel, which appears in most saves and was a term nearly all of them shared.
- **`gemini-embedding-001` is Matryoshka: a 1536-d request is a truncated 3072-d vector, and truncation destroys normalisation** — measured L2 1.000000 full against 0.691743 truncated. Cosine hides it; `<->` and `<#>` would not. Normalise client-side. Confirmed too that the API returns 3072 by default and 1536 only when `outputDimensionality` is sent.
- **A k-NN search has no "no match".** Before a distance cutoff existed, `zzzzqqq` returned the user's whole library. The cutoff (0.40) was measured — real hits land at 0.27–0.37, real misses at 0.42–0.50 — but on three saves and seven queries, so treat it as provisional.

**Embeddings are the one Gemini call not behind `BudgetApproved`, deliberately** — their pool is separate from the generation models', so counting them would throttle saves for nothing. That exception is stated loudly in `EmbeddingClient` precisely because the rule it breaks is otherwise absolute.

**The escalation gate's thresholds are guesses, and that is the tier's real open item.** `min-mean-confidence: 60` was sanity-checked against two extremes only — a clean synthetic card (95) and a textless clip — never measured. The thirty-Reel eval set in Phase 4 is what turns it into a number, and both failure directions are silent without it: too strict burns the 20-RPD Flash pool, too loose ships invented ingredients nobody reports. Everything the tier has read so far has been a fixture it generated itself; real text over photographs, motion blur and stylised fonts are exactly where tesseract fails hard rather than gracefully, and none of that is covered.

**Phase 4 — object behaviors — landed 2026-08-07** ([docs/next-phases.md](docs/next-phases.md#phase-4--object-behaviors-client--postgres-zero-ai)): the one mechanism (`save_item_states`, `V12__save_item_state.sql`) plus all six per-type behaviors from the doc's table — checklist ticks, watchlist watched/rating, workout exercise completion + rest timer, course section-done, recipe cook mode + serving scaling, and place/itinerary Maps deep links. Zero AI cost, exactly as scoped.

- **One table, one endpoint, per the doc's sketch almost verbatim** — `save_item_states (save_id, user_id, item_path, state jsonb)`, composite PK, `PATCH /v1/saves/{id}/item-state` (`{itemPath, state}` in the body, chosen over `PUT .../items/{path}/state` because `itemPath` values like `"exercises[2]"` would need URL-encoding as a path segment, and every other sub-resource mutation on `SaveController` already puts everything but the save id in the body). `SaveItemStateService` is `JdbcClient`-based like `ShoppingListService`, for the same reason: no interesting object graph, just an upsert keyed on a composite id, and JPA would buy nothing but a lazy-loading question. Write is `on conflict ... do update set state = excluded.state` — full replace, never a merge, the same rule the shopping list fold and the digest already follow.
- **State is per (save, user), not per save** — same reasoning as `save_votes` (V7): two Space members tick their own copy of a shared checklist independently. Access is enforced by delegating to `SaveService.getForUser` (own save, or a save in a Space the caller belongs to) before every write, never by trusting the path.
- **`GET /v1/saves` and `GET /v1/saves/{id}` both embed the caller's states now**, batched — `SaveItemStateService.statesForSaves` is one query for a whole feed page rather than N+1, the same "N could grow with page size" reasoning as the search endpoint's `findAllById` batching. `SaveResponse.itemStates` is omitted (not `{}`) when there is none, so an untouched save costs no extra bytes.

**The app is local-first as of 2026-08-09: L1–L5 of [docs/local-first.md](docs/local-first.md) all landed, and that plan is complete.** Every read screen now reads a local store through `useLive` and re-renders when it changes; `app/src/local/sync.ts` is the **only** consumer of `repo`, which is demoted to the network layer. A cold start with a warm store paints the feed, the Continue rail, the groups grid and the Spaces strip with no spinner at all. *(The rest of this section describes L1/L2 as they landed; L3–L5 below supersede the parenthetical caveats in it.)*

- **`Repository` could not be the seam, and is not.** All 48 methods return `Promise<T>`, which resolves once; stale-while-revalidate needs two emissions. `useLive(tables, read)` subscribes to a table-scoped change bus instead, so a write announces what it touched and only the queries naming that table re-run. One consequence landed exactly as predicted: `USE_MOCK_DATA` now *seeds* the store from `mockRepository`, so mock mode exercises the real local-first path instead of bypassing it — which is why the CDP verification below is meaningful rather than a check of a second code path.
- **The storage seam is at the store, and the web bundle proves it.** `expo-sqlite`'s web support is alpha and needs Metro WASM config *plus* `Cross-Origin-Embedder-Policy`/`Cross-Origin-Opener-Policy` headers for `SharedArrayBuffer`; headless Chrome on expo-web is this project's entire visual and interaction harness. So there are two implementations of ~20 typed methods — `sqliteStore.ts` on native, `memoryStore.ts` (AsyncStorage snapshot) on web — split by a Metro platform extension (`sqliteStore.web.ts`), not a runtime branch. Grepping the built web bundle finds no `openDatabaseAsync`, no `expo-sqlite`, no `enableChangeListener`: the alpha path is absent, not merely unused. `enableFTS` is deliberately still unset — FTS5 has no consumer until `searchLocal(q)` in L5.
- **`memoryStore` persists rather than being a pure shim, and that is a verification decision.** A session-scoped mock would make "paints from cache on a second load" untestable in the one environment this project can actually drive, so the central claim of the whole layer would have shipped unexercised.
- **`SaveResponse.itemStates` is populated by only three endpoints** — `GET /v1/saves`, `GET /v1/saves/{id}` and `PATCH .../item-state` use the 2-arg `SaveResponse.from`; `/search`, `/related`, `/spaces/{id}/saves` and `/groups/{id}/saves` use the 1-arg overload and omit the field. A cache that wrote one of those over a stored save would silently erase every ticked checkbox. Solved by **normalisation, not a merge rule**: `putSaves` strips `itemStates` before writing and only ever *adds* to `item_states`; the readers re-attach. A merge rule would have had to be remembered at six call sites and would be silently wrong the first time someone forgot. Pinned by a standalone assertion that no stored save row carries the field.
- **Groups and collections are derived on-device now, and cost no request at all.** `GET /v1/groups` and `GET /v1/collections` each load the user's entire ready library server-side and rebuild the tree per request — they are *views*, so once the store holds the whole library there is nothing left for those calls to say. `app/src/groups/tree.ts` ports `GroupService` (verified by replaying all twelve `GroupServiceTest` cases against it, its own fixtures included), `app/src/knowledge/facets.ts` ports `KnowledgeFacets` for the same reason the Java file exists — two copies drift — and `@/collections/merge` was already a port. Home's Continue rail is derived too: it was `GET /v1/saves/lifecycle` only because the feed was paged and filtering page 0 would miss anything older. Both endpoints stay implemented and keep `mockRepository` parity honest; the app simply stops calling them. **Four values in the port are load-bearing and must not be "tidied": `MIN_GROUP_SIZE = 5`, `ID_SEPARATOR = '~'` (group ids are route params, so a different id breaks deep links), `itemCount` counting *distinct* saves, and `[unclear]` never becoming a facet.**
- **Deriving locally means holding the whole library, not page 0.** The initial sync walks `GET /v1/saves` to exhaustion (100 a page, capped at 50 pages). The point at which that stops being fine is the same point at which the server's own full-library scan stops being fine, so neither side is newly constrained.
- **The API has zero sync primitives, so L1/L2 do not pretend otherwise.** No `since`, cursor, ETag, `@Version` or tombstone anywhere, and no `saves (user_id, updated_at)` index. Every task is a full fetch-and-replace; only the *shape* is the delta shape, so L4 changes `sync.ts` and nothing above it. Deletes are the part a delta cannot infer: seven hard-delete call sites, none leaving a record, so a deleted Space would live forever in any client that cached it.
- **Still unverified, same gap as the rest of the app:** `sqliteStore.ts` has never run. Web resolves the memory shim and there is no device or emulator here, so what is proven is the store *contract* and the screens on top of it, not that SQL.

**L3 (the outbox) and L4 (delta sync) landed 2026-08-09 too, closing the two gaps L1/L2 left open: writes went straight to the network, and reads were a full fetch-and-replace.** Now every write lands in the store and drains from a durable queue, and reads are one windowed `GET /v1/sync` (`V15__sync.sql`, `api/.../sync/`). Seven things generalise beyond this feature:

- **The revert logic is gone, and its absence is the deliverable.** Each of the ~11 write sites used to flip local state, fire a request, and on failure guess what to put back. That is wrong twice over: a failed request was simply *lost* (a tick made in a lift never happened), and "what to put back" is unanswerable once a second tap has landed — several sites had already given up and re-fetched instead, which cannot work in the offline case that needs it. Screens now call `@/local/writes` (write locally, queue the request, nothing else) and a write the server *rejects* is **surfaced** (`useOutbox` → `PendingWrites` on Settings) rather than rolled back. Silently undoing a change the app already showed as done is indistinguishable from "your tap never registered," which is the exact failure mode the whole layer exists to remove.
- **Last-write-wins is the real semantics here, not a compromise.** Every queued op is an absolute set (`favorite: true`, `state: {…}`) because every one of these endpoints is a documented full replace, never a merge. That is what makes a retry harmless with zero conflict-resolution code, and it is why `docs/local-first.md` rules CRDTs *out* rather than deferring them.
- **The idempotency key is generated once at enqueue and carried through every retry.** The failure it exists for is a request that reached the server and whose response was lost; a key minted per attempt is a different key and the server does the work twice. `POST /v1/saves` has had the column for this since V2 and no caller in the app until now.
- **The plan's `(updated_at, id)` keyset could not be built, and the reason is worth carrying.** A keyset is right for paging *one* table; `GET /v1/sync` pages **seven** against one shared cursor, and four have no scalar `id` to tie-break on (`save_item_states`, `entity_states`, `collection_overrides`, `space_members` all have composite PKs). A single `untilId` would be meaningless in six of them and would *skip* rows rather than resume after them. So the cursor is the timestamp alone and `SyncWindow` never ends a page *inside* a timestamp group: fetch `limit + 1` per type, and if any overflows, pull `until` back to the smallest overflowing boundary and re-read every type with an inclusive `<= until` and no limit. A capped page can exceed `limit` by one transaction's worth of rows; in exchange `until > since` strictly, so progress is guaranteed even when one group is larger than the page. **Design lesson: a cursor shape has to survive every table it is shared across, not just the one it was designed for.**
- **`replaceAll` must never reap a `local:` row.** A save created offline exists only on the device until its POST lands, so a full pull *cannot* mention it — reaping it deletes the user's save and orphans the outbox entry that creates it. Sharp, silent, and the one real interaction between L3 and the reaping refresh.
- **Read the audience *before* the delete.** `space_members` cascades away with a Space, so a tombstone written after the delete has nobody to address and every other member keeps the dead Space cached forever. `SpaceServiceTombstoneTest` pins the *ordering*, not just that a tombstone was written — the wrong order compiles, passes any weaker test, and loses every notification but the deleter's.
- **A schema bump is no longer free client-side.** `SCHEMA_VERSION` went to 2, and `outbox` is the first local table holding writes the server has never seen — so the standing "everything here is a cache, drop and re-fetch" rule no longer holds and every future bump has to weigh it.

Three requests per sync disappeared as a side effect: entity state used to be harvested from three `GET /v1/collections/{type}` calls because it had no other read path, and the delta carries it directly. The full pulls stay, but only on pull-to-refresh — `replaceAll` reaps rows the server no longer returns, which is the only way to recover from a *missed* tombstone, and a delta cannot do that by construction.

**One open question from the plan is now answered by measurement: a Postgres FK `on delete set null` cascade *does* fire the row-level `BEFORE UPDATE` trigger.** Probed against the live database with a throwaway user — deleting a Space moved its save's `updated_at` (`13:25:41.403104+00` → `13:25:43.307199+00`) and nulled `space_id`, so deleting a Space carries its saves in the ordinary delta for free and `DuplicateDetector`'s own `update saves set space_id = null` needs no tombstone. **L5 landed the same day and completed the plan: generalised idempotency (`V16`), local full-text search, and `expo-image`.** Search was the last read path in the app that could only answer from the network — an empty field, a spinner, and an error card offline. It now answers from the device's own index first and merges the server's hybrid result in behind it. Five things generalise beyond this feature:

- **A search index cost no `SCHEMA_VERSION` bump, and refusing one is the decision.** L4 left a standing warning that a bump is no longer free (the `outbox` holds writes the server has never seen), and this was the first change to meet it: bumping would have dropped a real outbox to install a table whose entire contents are a pure function of the `saves` rows beside it. So `saves_fts` is **rebuilt** at open on a count mismatch instead. The rule now written into `schema.ts`: *bump only for a change the local data cannot survive, never for one it can recompute.*
- **The FTS table is created outside `SCHEMA_SQL` and allowed to fail.** FTS5 is a compile-time SQLite option; inside the main schema batch, a build without it would have failed the whole `execAsync`, `openStore()` would have fallen back to the memory shim, and **a device would silently lose its entire local database to a missing search index**. Isolated, the worst case is that `searchLocal` runs the same linear scan the web build uses. Generic lesson: an optional capability must not share a failure domain with the thing that does not depend on it.
- **What is findable has one definition and both stores share it.** `searchText`/`searchTerms`/`scoreSearch`/`ftsMatchQuery` are pure and live in `store.ts`, so the FTS5 half and the scan half differ only in *ranking*, never in what they match — and the whole rule set could be executed under node rather than only typechecked. The body follows V11's rule exactly: **scalar leaves at any depth, JSON keys never** (a save's schema says `quantity`, `sets`, `rest` — "rest" is a plausible real query and must not match every workout), `[unclear]` stripped, title from `coalesce(title, name)`.
- **The local half is deliberately not debounced, and every local term is a prefix.** The 350ms wait exists because a server search spends an embedding call; an index read on the device has nothing to be economical with. And where `fullTextCandidates` prefixes only the last `tsquery` term (widening a server-side scan costs something), locally it costs a string comparison — so `chick past` matches "chicken pasta" while the user is still typing, and the local result set is a *superset* of the server's rather than a different one, which is what makes appending local-only hits safe.
- **A failed server search leaves the local results on screen and says why.** The old screen replaced everything with an error card, which offline read as "you have nothing" — the exact failure this whole layer exists to remove. Same rule in the merge itself: a server response must never *remove* a result the user could already see.

Server side, `IdempotencyService` puts the claim, the work and the response write in **one transaction** rather than claiming in `REQUIRES_NEW`: a failure then rolls back the claim with the work, so a retry genuinely retries instead of being told forever that a request which never happened is in flight. The concurrency that produces is better than the alternative, not a cost of it — a second request with the same key blocks inside `on conflict do nothing`, then replays the committed response or does the work, depending on how the first ended. The **stored response body is the point, not the avoided write**: answering a replay with `204` would leave a retried invite creation "successful" and the caller still without the code the request exists to produce. Client-side only `addComment` (the one queued op that creates a row) and `createSpace` send a key; `createInvite` deliberately does not, because two taps of "Invite" are genuinely ambiguous between a lost response and wanting a second link.

**Account and Space deletion landed 2026-08-13 — the first place either exists.** Space deletion already existed fully server-side (`SpaceService.delete`, owner-gated, tombstoned for every other member) with no UI ever built for it; account deletion had nothing at all, not even a stub. - **`AccountService.deleteAccount` (new `account/` package) orchestrates rather than owns a single transaction, deliberately.** It deletes every Space the account owns through `SpaceService.delete` (so tombstones fire for every other member), every save the account owns anywhere through `SaveService.delete` (ditto — including saves sitting in a Space someone else owns), leaves every membership it holds in Spaces owned by others through `SpaceService.removeMember`, deletes the `profiles` row (cascades subscriptions, usage counters, digests, entity states, item states, overrides, idempotency keys, its own tombstones), and only then calls a new `SupabaseAdminClient.deleteUser` — the Supabase Admin API call that actually revokes login and refresh tokens, last, because doing it first would cascade `profiles` away via Postgres's own FK before any of the tombstone-emitting steps above ran. Every step tolerates "already gone," which is what makes the whole thing safely re-callable rather than atomic — stated as a real tradeoff, not hidden: a failure between steps leaves real data already gone, and a retry finishes the job rather than starting over.

**Phase 1 of [docs/extraction-architecture.md](docs/extraction-architecture.md#phase-1--stop-the-bleeding-in-place-no-new-service) landed 2026-08-15 — the three in-place fixes for bugs that were live, not the dedicated extraction service the rest of that doc proposes.** F1 (no HTTP client anywhere had a timeout), F2 (SSRF in the link extractor) and F3 (unbounded response reads) are closed; F4–F10 and Phases 2+ are still open.

- **Every `RestClient` gets a connect and read timeout, via `RestClientConfig` rather than inside each client's own constructor.** The obvious approach — call `.requestFactory(timeoutFactory)` inside `GeminiClient`'s/etc. constructor — was checked against how the existing `MockRestServiceServer`-based tests actually bind: `MockRestServiceServer.bindTo(builder).build()` sets its mock factory on the builder *before* the client's constructor runs, and `RestClient.Builder.build()` snapshots the builder's state into an immutable `RestClient` — so whichever `.requestFactory()` call happens last, chronologically, before that snapshot wins. A constructor-side call would silently overwrite the mock in every existing test, turning them into live-network calls with no compile error to catch it. The fix instead gives each client with its own `weavr.*.timeout` property (`GeminiProperties`, `GroqProperties`, `RapidYtProperties`, `EnrichmentProperties` — shared by all three enrichers, `EmbeddingProperties`) a `@Qualifier`-named `RestClient.Builder` bean, resolved by Spring's DI container *before* the builder ever reaches a constructor; everything else (`LinkExtractor`, `PdfExtractor`, `ProcessSaveHandler`, `SupabaseAdminClient`, `SupabaseStorageClient`) falls back to one default-timeout bean via Spring's name-matching disambiguation (the bean is named `restClientBuilder`, matching every one of those constructors' existing parameter name). None of this touches test code at all, by construction: every `*ClientTest` builds its `RestClient.Builder` from the bare static `RestClient.builder()` factory method, never through Spring, so the qualifiers and the whole `RestClientConfig` class are inert there — confirmed by the full suite passing unchanged. The one easy-to-miss part of this pattern: the *default* bean also has to be `@Scope("prototype")`, not just the named ones — a singleton default would hand the same mutable builder instance to five unrelated components, and the first one to call `.defaultHeader(...)` (`LinkExtractor`'s browser-like User-Agent) would leak that header onto all the others.
- **SSRF defence and a streaming size cap are one new class, `SafeUrlFetcher`, shared by `LinkExtractor` and `ProcessSaveHandler`'s image download** — the two call sites the doc's own Phase 1 bullet names. It resolves the host via `InetAddress.getAllByName` and rejects loopback/link-local/site-local/multicast/any-local addresses *and* IPv6 unique-local (`fc00::/7`, which `isSiteLocalAddress()` does not cover — only the deprecated `fec0::/10` range) before issuing any request, re-checks on every redirect hop (redirects are followed manually, capped at 3, specifically so a URL that is only unsafe *after* redirecting is still caught), and reads the response body in a bounded loop that throws the instant a configurable ceiling is crossed rather than buffering the whole thing first. **Stated rather than solved: this closes the obvious case (a URL whose DNS record or literal IP is already private) but not a DNS-rebinding attack that changes the record's answer between the validation check and the connection a moment later** — closing that needs pinning the actual socket to the address that was validated, which is exactly what Part D's Security section scopes to the dedicated extraction service, not this in-place fix. `PdfExtractor.download` has the identical unvalidated-fetch shape and was deliberately left untouched — it's outside Phase 1's own named scope, and touching it would have meant reconciling `SafeUrlFetcher`'s new streaming-abort semantics with `PdfExtractor`'s existing post-hoc `pdf_too_large` check and its pinned test message.
- **`WEAVR_RAPID_YT_API_KEY` added to `.env.example`** (F10) — it was already in `render.yaml` and `application.yml`, so a fresh clone was silently running with the provider disabled.

**Phase 2 of [docs/extraction-architecture.md](docs/extraction-architecture.md#phase-2--extractor-refactor-behaviour-first-boundary-second) landed 2026-08-15 — the RapidAPI probe's retry/ranking behaviour, a real decision on the one open design question (F5), and the `SourceExtractor` seam.** F4, F6 and F8 are closed; F5 is decided (fail fast, not routed through the provider); F7 and F9 are still open (out of this phase's own named scope).

- **F4 — `RapidYtClient.probe` retries up to twice, full jitter, only for what's worth retrying.** The `onStatus` handler on the `/dl` call previously threw a plain `RuntimeException` with the status code only interpolated into a message string, discarding it as a value — a new `RapidApiStatusException` carries the int instead, so `probe`'s retry loop can ask `status == 429 || status >= 500` rather than string-matching. A connection failure (`ResourceAccessException`) is retried the same way. A 404 or any other 4xx, and a JSON parse failure, are **not** retried — retrying won't make a deleted video reappear or a malformed response parse — so they return `Optional.empty()` on the first attempt, same as before. Backoff is exponential (200ms base, capped at 2s) with **full jitter** (sleep a random duration between zero and the capped delay, not a fixed wait) — the standard defence against every retrying caller waking up in lockstep and re-hitting RapidAPI at the same instant.
- **F6 — caption tracks are ranked by parsed prose length, not "whichever RapidAPI listed first."** `bestTranscript` tries up to 5 candidate tracks (a stated safety bound, not a measured typical count — RapidAPI's response carries no manual-vs-auto flag to prefer, unlike yt-dlp's own `subtitles`/`automatic_captions` split) and keeps the longest parse, mirroring `YtDlpClient.bestCaptions`'s existing "an auto-generated track is bigger but carries less text, so rank by output not by size or position" rule from the same doc's first investigation. A track that fails to fetch no longer sinks the others — each candidate is tried independently.
- **F8 — `/live/` added to `YT_ID`.** `m.youtube.com` and `music.youtube.com` needed no regex change at all: the pattern was never anchored to the string's start, so `youtube.com/watch?v=` already matched as a substring of either subdomain's URL — confirmed by a new test asserting all nine shapes extract the same id, not assumed from reading the regex.
- **F5 decided: fail fast, not "route ASR/OCR through the provider."** The RapidAPI response `RapidYtClient` actually parses carries `title`/`channelTitle`/`description`/`lengthSeconds`/`thumbnail`/`captions.captionTracks` and nothing else — no audio or video download URL is read anywhere in the file. Building the alternative would mean assuming an unread field exists on the live endpoint, adding a `RapidYtClient` dependency to both `AsrTranscriber` and `VisualTextExtractor` (neither has one today), and its own retry/error-classification work — real Phase-3-dedicated-service territory, not a same-day in-place fix, and not something to build on an unverified assumption about a third-party response shape. So: when RapidAPI's metadata and every caption track it offers are both too thin, `ExtractionCascade` now throws `PermanentJobException("youtube_no_usable_text", ...)` immediately instead of falling into `continueFromMetadata`'s ASR/visual tiers, which would otherwise call `ytDlp.downloadAudio`/`downloadVideo` straight at YouTube — the confirmed-dead-on-Render path (8/8 real URLs hit the identical bot-check error, cookies and player-client override both tried and both failed). The economics hold independent of the Render block too: spending a full yt-dlp video download on a platform whose fast metadata path already came up empty contradicts the reason that path exists. **Stated tradeoff, not hidden**: a hypothetical non-Render deployment where yt-dlp-against-YouTube still works loses that fallback for captionless YouTube saves specifically — the code has no way to distinguish "Render" from "residential dev machine" at runtime, and this fix does not add one.
- **The `SourceExtractor` seam is one new interface, `ExtractionCascade implements` it, and one field-type change.** `ProcessSaveHandler` already depended only on `ExtractionCascade` (confirmed by grep before touching anything — no controller or other handler anywhere references `YtDlpClient`/`RapidYtClient` directly), so the whole change is: `SourceExtractor.extractFromUrl(String, UUID)` returning `ExtractionCascade.Extraction` (kept nested where it already lived rather than promoted to a standalone type — there is exactly one implementation today, and promoting it now would be the kind of change that "costs nothing to introduce" explicitly is not), `ExtractionCascade implements SourceExtractor` with an `@Override`, and `ProcessSaveHandler`'s constructor parameter retyped from `ExtractionCascade` to `SourceExtractor`. `AsrTranscriber`/`VisualTextExtractor` still hold `YtDlpClient` directly — they're internal collaborators of the one `SourceExtractor` implementation, not external callers reaching around it, so the gate doesn't apply to them.

**Phase 4 of [docs/extraction-architecture.md](docs/extraction-architecture.md#phase-4--storage-and-artifacts) landed the same day — `ArtifactStore` writes to real Supabase Storage now, not local disk, closing the one Phase 3 explicitly flagged as its own stand-in.** Only the backing store changed; the signing contract callers on both sides of the wire are written against (opaque, HMAC-signed, expiring `sig:` ref) did not.

- **The per-save prefix lives in the signature, not a side table.** `ArtifactStore.put(prefix, kind, bytes)` sanitises the caller-supplied prefix — the save id `Idempotency-Key` already carries, threaded down through `ExtractController` → `ExtractionOrchestrator` → `VisualExtractor` — to `[A-Za-z0-9_-]` (a blank or absent one gets a random id instead, never rejected), and signs `prefix:id.expiresAt` with `:` as the internal separator, deliberately not `/`, so the existing `refDoesNotExposeTheUnderlyingStoragePath` test keeps holding unchanged. `read` reconstructs `{prefix}/{id}` from the verified payload and asks storage for it directly — no registry lookup at all, which is *why* this survives a restart where Phase 3's in-memory id→path map didn't.
- **Upload/download/delete are a plain concatenated URL string, not a `RestClient` URI template — deliberately.** `.uri("/object/{bucket}/{path}", bucket, objectPath)` would have had `UriComponentsBuilder` percent-encode the `/` inside `objectPath` (the very thing separating the per-save folder from the artifact id), corrupting the nesting this phase exists to add. Built the same way `api`'s own `SupabaseStorageClient.upload` already does — string concatenation, not a template — which is also why this shape carries the same live-verified confidence that class already has for `PUT`; `GET`/`DELETE` reuse the identical path construction.
- **"Consumed" and "orphaned" are two different deletion paths, not one.** `ArtifactStore.read` deletes the object the instant it's successfully redeemed — a completed save's artifact is gone before the backend's own response returns, satisfying the doc's gate directly rather than waiting for a timer. The pre-existing `@Scheduled sweep()` is retargeted from the old in-memory registry to the real bucket (`SupabaseArtifactStorage.listPrefixes()`/`.list(prefix)`, `POST /storage/v1/object/list/{bucket}`) and is what catches anything nobody ever redeemed — a crashed job, a response that never reached the backend. Both are best-effort: a failed delete or a failed listing is logged and swallowed, never thrown, since neither may sink a request that otherwise succeeded.
- **The listing call is the one piece of this phase that is reasoned about, not measured, and `SupabaseArtifactStorage`'s own class doc says so.** Upload/download/delete mirror a shape this codebase has already run live (via `api`'s screenshot uploads); `POST /object/list/{bucket}` has not. A wrong assumption there degrades to "the sweep finds nothing" — logged, harmless — because neither a read nor a write goes through the listing code at all.

**Click-path audit, 2026-10-04: 44 handler-level bugs found, the 6 high-severity ones and two shopping-list races fixed.** A `/click-path-audit` traced every button's handler against a map of what each store/outbox/sync action sets *and resets*. The remaining medium/low findings were fixed the same day — next entry.
- **Root cause, sync layer: echoes and fetches overwrote newer local writes.** Each sender adopted the server's echo via `patchSave`, which *replaces* the item-state map, so tick A then B un-ticked B until B sent (up to the 5-min backoff cap). `supersededLocally` in `sync.ts` now skips an echo while a newer pending entry for the same `entityId` exists. Shopping-list fetches (personal and Space) go through `fetchShoppingList`: it refetches if a shopping write landed mid-fetch, then re-applies still-queued ticks/clears (`overlayPendingShopping`, pure, in `outbox.ts`).
- **"Clear checked" could overtake a tick in backoff** (it was queued with `entityId: null`), so cleared items came back checked. All ops on one list now share `shoppingListKey(spaceId?)`.
- **Deleting a just-sent comment, or unpinning a just-made pin, still posted it.** The screen dropped the `pending:` placeholder and queued nothing. Placeholders are now `local:` ids returned by `writeComment`/`writeEntityComment`/`writePin`. The delete is queued under the create's key, so it is sent after the create, and resolves the real id through an in-memory `sentIds` map. Pin and unpin now share one key (previously unpin used the pin id, so an unpin in backoff could land after a re-pin).

- **Appearance → Sign out stranded the user on Appearance**, the same bug `SettingsScreen.leaveAndSignOut` already fixed. It now `dismissAll()`s first.

- **Found: concurrent SQLite transactions.** expo-sqlite's `withTransactionAsync` is not exclusive, and every `@/local/writes` helper fires its store write and `sync.enqueue` (also a transaction) in the same tick. The first offline capture logged `NativeDatabase.execAsync … cannot start a transaction within a transaction`. Its `local:` row was never stored (the rejection was swallowed by the `void` at the call site), while its outbox entry went in. `memoryStore` can't reproduce this, so no browser run ever could. **Fix:** `sqliteStore` serialises every write method through one promise chain, reads included, which also closes `patchSave`'s read-modify-write window. After the fix the same capture stored its row and no further transaction errors were logged. That is one failure before and one success after on a timing race, so it's strong evidence rather than proof.
