Analytics plan · PostHog · Sep 2026

Measuring whether Capture → Extract → Find/Act actually holds.

Not a plan to collect everything PostHog makes easy — a plan to answer seven specific product questions, built around how Weavr's pipeline and screens actually work today, not a generic mobile-analytics template.

Read this before anything else

Two places this plan corrects the obvious draft, because the product doesn't match the generic shape:

  • Most captures never run through the app's JS layer. Android's silent share-intent receiver enqueues locally and uploads in the background — the app never opens. Capture/extraction/save events are emitted server-side, keyed by user id, or the majority of activity is invisible to analytics.
  • The personal library has no "create a collection" action — groups and collections there are fully derived on-device. An collection_created event would track something that doesn't exist. Real user-driven organizing only happens inside Spaces.
A

Analytics philosophy

Three rules govern every decision in this document:

  1. An event answers one of the seven questions in the brief, or it doesn't ship. "We could track this" is never sufficient reason.
  2. Server truth beats client-reported truth wherever both exist. Weavr already treats the job queue and the RevenueCat webhook as the source of truth for save status and entitlement — analytics keys off the same source, not a client's optimistic guess.
  3. An analytics property is never a second copy of user content. The privacy policy currently promises zero event-tracking; the surviving promise once that changes is "behavioral metadata only," never "the content, tagged."
C

North Star metric candidates

There isn't enough evidence yet to lock one in — picking now would mean justifying it backwards. Three candidates, ordered by how soon they're trustworthy.

Week-1 second-capture rate

% of newly activated users who capture a second time within 7 days. Cheapest to trust at low post-launch volume; isolates habit formation from just reopening the app.

Recommended starting metric

Saves revisited / active user / week

save_viewed where the save is >24h old. Tests whether Extract→Organize→Find delivers — not just whether Capture does.

Fallback if #1 doesn't predict D30

Weekly successful captures / retained user

Combines quality and volume into one number. Good exec-summary metric once mature — too composite for day-to-day steering.

Revisit once mature
D

Activation definition

  • Activation event: save_ready with is_first_save = true — not sign-in (no value delivered) and not capture_received (a failed extraction never delivers the "aha" moment).
  • Activation window: 24 hours from sign_in_completed — generous enough to absorb a busy-queue day, tight enough that a multi-day gap is a real problem.
  • Drop-off points, in order: sign-in→first capture (discovery problem) · capture→extraction (pipeline reliability) · extraction→ready (should be ~100%; any gap is a bug) · ready→viewed (did the notification close the loop).
  • Time-to-value: median and p90 of sign-in → first save_ready.

F

Identity strategy

  • distinct_id = Supabase user id on both client and server — the same id every API service already authorizes against, so one PostHog person merges both streams for free.
  • Pre-auth window is thin but real — index.tsx redirects straight to sign-in with no session, so only the sign-in screen itself is anonymous. Use PostHog's anonymous id there, then identify() the moment a session establishes; the standard anonymous→identified merge handles the rest.
  • posthog.reset() on sign-out — skipping this is the most common way a second account on the same device gets mismerged into the first person.
  • Server-side is always authenticated — every job belongs to a user, so there's no anonymous concept to handle there.
  • Multi-device — identifying with the same id on every device, every session restore, merges devices automatically. No dedicated "device changed" event needed.
G

Privacy strategy

Should collect

Feature usage · screen/flow navigation · success/failure and error type · timing/latency · knowledge_type, model_used, confidence, escalated · app version, platform · coarse buckets.

Should never collect

Raw extracted text, save titles/thumbnails, source URLs, search query strings, Space comment text, shopping-list item text, workout notes, auth tokens, anything from a captured file, per-frame OCR/ffmpeg internals.

Make it structurally impossible, not just a review hope

Define every event's property shape as a typed interface with only enum-like/numeric/boolean fields — no free-text field exists in the type to misuse. See §O.

Phase 1 blocker

legal/privacy.html currently states Weavr has "no analytics SDK... no event-tracking pipeline in the app." This plan falsifies that live claim. Updating that page and Play's Data Safety form happens before shipping, not after.

J

Funnels

Build at launch

  • Activation — sign-in → capture received → extraction completed → first save ready
  • Capture reliability (ongoing) — capture received → extraction completed / failed
  • Retrieval — search performed → result opened

Deferred

A Space-adoption funnel (created/joined → pinned) — Spaces are secondary; the personal capture→retrieval loop needs proving first. The brief's draft "Organization funnel" (item_saved → collection_created → item_added_to_collection) is dropped entirely — nothing in the personal library maps to it.

O

Code architecture

app/src/analytics/

events.ts — one const per event plus a discriminated union mapping event → property shape, so track() is fully typed and a free-text field cannot compile in. client.ts — thin wrapper over posthog-react-native: init, identify, reset (wired to sign-in/sign-out), one typed track(). No-ops in dev unless a debug flag is set.

api/.../analytics/

AnalyticsService.java — wraps PostHog's capture endpoint via RestClient, same pattern as the existing Gemini/Groq clients; async fire-and-forget so a PostHog outage never fails a save. AnalyticsEvents.java — event-name constants kept in sync with the TS side by convention. Called from the save-processing handlers, the upload controller, and the RevenueCat webhook handler.

R

What NOT to track

  • Raw save titles, extracted text, thumbnails, URLs, search query strings, comment/list/exercise text — anything echoing captured content
  • Per-frame OCR/ffmpeg internals — that's log/APM data, not a product event
  • A screen_viewed for every one of the ~19 routes — skip anything already covered by a more specific event
  • Every frame of the tab-swipe gesture animation — UI mechanics, not signal
  • A separate event per settings toggle — bundle the handful that matter
  • Hand-rolled app_crashed from a JS try/catch — pair with a real crash reporter instead
  • Any "collection_created" analogue for the personal library — it isn't a user action there
  • Session replay — Weavr's content is personal screenshots, photos and PDFs

Before launch

  • Blocking, first: update legal/privacy.html and Play's Data Safety form

  • All 18 essential events above; activation + capture-reliability funnels; dev/prod key separation
Phase 2

First 2 weeks

  • group_opened, collection_opened, space_created, space_joined
  • Retrieval funnel; cohorts; D1/D7/D30 retention report; a real crash reporter
Phase 3

After meaningful usage

  • save_field_edited once field-editing ships; Space-adoption funnel
  • Feature-adoption-vs-retention analysis; North Star lock-in; first real experiments
Don't yet

Not worth building now

  • A/B testing / feature flags — no volume to power a result for months
  • Per-button UI interaction tracking; native pre-upload queue-lag instrumentation; session replay
